# Engineering Rules

## 코드 작성 전 체크리스트

- [ ] 이 함수/모듈의 책임이 정확히 하나인가? (SRP)
- [ ] 지금 당장 필요한 것만 만들고 있는가? (YAGNI)
- [ ] 더 단순한 방법이 있는가? (KISS)
- [ ] 같은 로직이 이미 다른 곳에 있지 않은가? (DRY — 아래 "중복" 기준)
- [ ] 새 함수·클래스·파일이 다음 중 하나를 하는가? 아니면 만들지 않는다.
      - 호출자가 몰라도 되는 결정이나 복잡함을 숨긴다
      - 코드만 봐서는 드러나지 않는 의도에 이름을 붙인다
      - 지켜야 할 조건(불변식)을 한 곳에서 강제한다
      - 지금 필요한 교체 지점이다 (테스트 대역 등)

## 구조 설계 원칙

### 함수·메서드
- 함수는 **한 가지 일**만 한다. 이름만 보고 무엇을 하는지 알 수 있어야 한다.
- 함수 내부의 **추상화 수준을 일관**하게 유지한다. `connectDB()`와 `i++`가 같은 함수에 있으면 안 된다.
- 파라미터는 **4개 이하**를 유지한다. 초과하면 Parameter Object로 묶는다.
- 함수 길이가 화면을 초과하면 분리를 검토한다.
- 결과는 **반환값으로** 돌려준다. 여러 함수가 같은 결과 변수(out 파라미터)를 넘겨받아 채우게 하지 않는다. 객체 상태로 알 수 있는 정보는 상태에서 계산한다.
- 두 줄을 넘는 조건식은 의도를 드러내는 이름의 함수로 꺼낸다. (Decompose Conditional)

### 이름
- 이름은 **의도를 드러낸다**. `data`, `temp`, `x`, `flag`, `val`은 쓰지 않는다.
- 이름에 타입 정보를 넣지 않는다 (`strName`, `intCount` 금지).
- 매직 넘버·문자열은 이름 있는 상수로 교체한다 (`if (status == 3)` 금지).
  - 단, 의미가 바로 옆 코드나 주석에서 보이는 값은 리터럴로 쓴다: 문법상 글자 위치, 진법(10, 16), 고정 길이, 관용값, 참고한 알고리즘의 숫자. 이름을 붙이면 읽는 사람이 정의를 찾아가야 해서 오히려 읽기 어렵다.
  - 상수는 쓰는 곳 가까이 둔다. 한 파일에서만 쓰면 그 파일 위쪽에, 여러 파일이 쓰거나 조정할 값이면 공용 상수 모듈에 둔다.
- 함수 이름과 실제 동작이 일치해야 한다. 부수 효과가 있으면 이름에 드러낸다. (POLA)

### 모듈·클래스
- **높은 응집도**: 모듈 내부 요소들은 하나의 목적으로 묶인다.
- **낮은 결합도**: 모듈 간 의존성을 최소화한다. 변경이 파급되지 않아야 한다.
- **데메테르 법칙**: `a.getB().getC().doSomething()` 형태의 체인을 만들지 않는다. 직접 아는 객체하고만 대화한다.
- 인터페이스(추상) 의존과 확장 지점(DIP·OCP)은 **교체·변경이 실제로 반복되는 곳**에만 둔다. 구현이 하나뿐이고 바뀔 계획이 없으면 구체 타입에 직접 의존한다.

### 중복
- 같은 **지식·결정**이 두 곳 이상에 있으면 추출한다. 기준: 한쪽을 고칠 때 다른 쪽도 반드시 고쳐야 하는가.
- 호출 문법이 반복되는 것(같은 함수를 같은 모양으로 부르는 것)은 중복이 아니다.
- **우연한 유사성**(코드가 비슷하지만 변경 이유가 다른 경우)은 추출하지 않는다.

### 추상화 경고 신호
아래에 해당하면 만들지 않거나 지운다 (Inline Function).
- 몸체가 받은 인자를 그대로 다른 함수에 넘기는 한 줄뿐이다 (pass-through)
- 이름이 감싼 호출보다 정보를 더 주지 않는다
- 감싼 것과 감싸지 않은 직접 호출이 함께 쓰인다 (같은 일을 하는 방법이 둘)

## 방어적 프로그래밍 원칙

- **Fail Fast**: 잘못된 입력은 깊이 들어가기 전에 즉시 거부한다.
- **입력 검증**: 외부에서 온 모든 데이터(네트워크, 파일, CLI, 사용자 입력, 저장소에서 읽은 값)는 신뢰하지 않는다. 진입점에서 검증한다.
- **에러를 삼키지 않는다.** 빈 catch 블록, 무시한 반환값·에러 코드, 처리하지 않은 Promise rejection을 남기지 않는다. 의도적으로 무시하면 이유를 주석으로 남긴다.
- **리소스는 반드시 정리한다.** 파일 핸들, 소켓, 이벤트 리스너, 타이머, 구독은 모든 경로(정상·오류·언마운트)에서 해제한다.
- 에러 메시지는 **원인과 컨텍스트**를 담는다. "Error occurred"는 에러 메시지가 아니다.

## 테스트

- 동작을 바꾸면 그 동작을 검증하는 테스트를 추가하거나 수정한다.
- 테스트는 구현 세부가 아니라 **공개된 동작**을 검증한다.
- 실패하는 테스트를 지우거나 skip해서 통과시키지 않는다. 테스트가 틀렸다고 판단되면 근거와 함께 보고한다.

## 코드 작성 후 자가 검토

### **정확성**
- 엣지 케이스(빈 값, 경계값, null, 최대·최소)를 처리했는가?
- 에러 경로가 모두 처리되었는가?

### **가독성**
- 코드를 처음 보는 사람이 이름만 보고 흐름을 따라갈 수 있는가?
- 이번에 **새로 작성한** 복잡한 로직에 "왜(why)" 주석이 있는가? (무엇(what)은 코드가 설명한다. 기존 코드의 주석은 건드리지 않는다.)

### **구조**
- 중복된 지식·결정이 생기지 않았는가?
- 의존성이 의도하지 않게 늘어나지 않았는가?

### **군더더기**
- 이번에 추가한 함수·타입·파일마다: 지우고 호출부에 펼치면 더 읽기 어려워지는가? 아니면 지운다. (Beck "Fewest elements")
- 같은 일을 하는 방법이 두 가지가 되지 않았는가? 래퍼를 만들면 모든 직접 사용을 바꾸고, 아니면 만들지 않는다.

### **보안**
- 외부 입력이 검증 없이 사용되지 않는가?
- 민감한 정보(비밀번호, 토큰, 키)가 코드에 하드코딩되지 않았는가?

## 금지 사항

- 전역 상태(global state)를 무분별하게 사용하지 않는다.
- 주석으로 나쁜 코드를 설명하려 하지 않는다. 코드 자체를 개선한다.
