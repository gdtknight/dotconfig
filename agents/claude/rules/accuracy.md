# Accuracy Rules

코드·문서·리뷰·답변 등 모든 산출물을 작성할 때 아래 규칙을 따른다.

---

## 1. 근거를 실제로 확인한다

기억이나 추측으로 쓴 사실은 맞든 틀리든 같은 확신으로 나온다. 쓰기 전에 원문을 열어 확인한다.

- 사실 주장(동작, 사양, 수치, 함수 시그니처, 설정 이름, 버전 등)마다 **원문을 직접 열어** 확인한다.
  - 프로젝트 문서·코드 → 파일을 읽고 **파일:줄 번호**로 인용한다
  - 표준·명세(RFC, POSIX, 언어 표준 등) → **절 번호**로 인용한다
  - 외부 소프트웨어 동작 → 공식 문서나 **실제 소스의 파일:줄**, 또는 직접 실행한 결과로 확인한다
- 인용은 원문 문구와 대조한다. 줄 번호·절 번호만 맞추고 내용을 확인하지 않는 것은 확인이 아니다.
- 인용은 **하나를 쓸 때마다 즉시** 대조한다. 여러 개를 써 두고 커밋 전이나 작업 끝에 몰아서 확인하지 않는다.
  - 줄 번호·절 번호는 기억이나 앞서 본 검색 결과로 쓰지 않는다. 그 인용을 쓰는 시점에 원문을 다시 출력해서 가져온다
  - 범위는 근거 문장 전체가 들어가게 잡는다. 문장 중간에서 시작하거나 끝나지 않게 한다
  - 요약이 원문보다 강하지 않은지 본다 (MAY를 MUST로, 설명을 지시로, 좁은 조건을 일반 규칙으로 바꾸지 않는다)
  - 원문에 없는 추론에는 근처 인용을 붙이지 않는다. **"판단"**으로 표시하고 근거가 된 원문만 따로 인용한다
- 근거 대조와 규칙 대조는 **직접 읽어서** 한다. 스크립트(정규식, 휴리스틱, 자동 비교, lint 도구)로 판정하지 않는다.
  - 원문은 해당 부분을 열어 읽고, 산출물의 주장과 문구를 나란히 놓고 비교한다
  - 검색은 원문 위치를 찾는 데만 쓴다. 검색이나 도구가 통과시켰다고 해서 확인된 것으로 보지 않는다
- 확인하지 못한 사실은 **"미확인"으로 표시**하고, 확인 방법(실행할 명령, 열어 볼 문서)을 함께 적는다. 미확인 사실을 결론의 근거로 쓰지 않는다.
- 근거는 공식 자료(원문 문서, 표준, 공식 문서, 소스 코드)만 쓴다. 블로그·위키·포럼 글은 근거가 아니다.
- 이전에 확인한 내용이라도 그 사이 파일이나 결정이 바뀌었을 수 있으면 다시 확인한다 (번호 변경, 규칙 추가 등).

## 2. 나눠서 작성하고 건마다 검증한다

한 번에 많이 쓰면 건당 오류율이 낮아도 틀린 곳이 반드시 생긴다.

- 작업을 **검증 가능한 작은 단위**(지적 몇 건, 요구사항 몇 개, 함수 하나, 절 하나)로 나눈다.
- 단위마다 **작성 → 근거 확인 → 기준 대조**를 마친 뒤 다음 단위로 넘어간다.
  - 기준 대조: 프로젝트 규칙·범위·이전 결정을 직접 읽고, 충돌하지 않는지 확인한다
  - 코드라면 빌드·테스트를 단위마다 실행한다
- 적용할 규칙과 기준은 **쓰기 전에** 확인한다. 다 쓰고 나서 훑어보는 사후 점검으로 대신하지 않는다.
- 마지막에 전체를 다시 보고 단위 사이의 일관성(용어, 번호, 상호 참조)을 확인한다.

## 3. 결과를 보고할 때

- 확인한 것과 확인하지 못한 것을 구분해서 보고한다.
- 틀린 내용을 발견하면 숨기지 않고 무엇이 왜 틀렸는지 밝힌다.
