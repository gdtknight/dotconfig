## 운영 방법론

코드를 분석해 주석을 작성하고 포맷을 정리한다. 4개 Phase를 순서대로 수행한다.

---

### Phase 1 — 코드 분석

대상 파일을 읽고 다음을 파악한다.

- 파일의 목적과 포함된 모듈/기능
- 주석이 없거나 불충분한 함수·구조체·열거형·매크로
- 이미 존재하는 주석의 품질과 일관성
- 코드 포맷 현황 (들여쓰기, 줄 길이, 브레이스 스타일)
- 언어 (C, C++, Python 등) → 언어별 Doxygen 적용 방식 결정

### Phase 2 — Doxygen 주석 작성

#### 작성 철학 (실무 기준)

주석의 목적은 **WHY**를 설명하는 것이다.
- WHAT은 코드가 이미 보여준다 → 코드가 하는 일을 그대로 반복하는 주석은 쓰지 않는다
- HOW는 구현 내부에 있다
- WHY(왜 이렇게 설계했는가), 비직관적인 결정, 알고리즘 출처, 주의사항을 쓴다

```c
/* ❌ 나쁜 주석 — WHAT을 반복 */
/* i를 1 증가시킨다 */
i++;

/* ✅ 좋은 주석 — WHY를 설명 */
/* 0-indexed이므로 출력 전 1을 더해 1-indexed로 변환 */
i++;
```

#### 파일 헤더 (모든 파일 상단)

```c
/**
 * @file   filename.c
 * @brief  파일의 한 줄 요약
 *
 * 파일이 담당하는 역할과 설계 결정에 대한 설명.
 * 외부 사용자가 이 파일을 처음 볼 때 알아야 할 것.
 *
 * @author 작성자
 * @date   YYYY-MM-DD
 */
```

---

#### 함수 주석

```c
/**
 * @brief  함수가 하는 일을 명령형으로 한 줄 요약
 *
 * 필요한 경우 더 자세한 설명.
 * 비직관적인 동작, 알고리즘 참고문헌, 설계 결정 이유를 여기에 쓴다.
 *
 * @param[in]     name    입력 파라미터 설명 (함수가 읽기만 함)
 * @param[out]    result  출력 파라미터 설명 (함수가 값을 씀)
 * @param[in,out] buf     입출력 파라미터 설명
 *
 * @return 반환값 설명
 * @retval  0  성공
 * @retval -1  실패 (errno 설정됨)
 *
 * @note    중요한 전제조건이나 사용법 주의사항
 * @warning 잘못 사용하면 발생할 수 있는 위험
 * @see     연관_함수()
 */
```

**`@param` 방향 지시자 기준:**

| 지시자 | 사용 시점 |
|--------|---------|
| `[in]` | 함수가 읽기만 하는 파라미터 |
| `[out]` | 함수가 결과를 저장하는 포인터 |
| `[in,out]` | 읽고 수정하는 파라미터 |

**간단한 함수 (getter 등)는 `@brief`만 사용한다:**
```c
/** @brief 소켓의 현재 수신 버퍼 크기를 반환한다. */
int get_recv_buf_size(int fd);
```

---

#### 구조체·클래스

```c
/**
 * @brief  구조체가 표현하는 개념 한 줄 요약
 *
 * 이 구조체가 왜 이 필드들로 구성되었는지,
 * 어떤 맥락에서 사용되는지 설명한다.
 */
typedef struct s_client {
    int     fd;        /**< 클라이언트 소켓 파일 디스크립터 */
    char    *buf;      /**< 수신 데이터 버퍼 (동적 할당) */
    size_t  buf_len;   /**< buf의 현재 사용 중인 바이트 수 */
    size_t  buf_cap;   /**< buf의 총 할당 크기 */
} t_client;
```

#### 열거형

```c
/**
 * @brief HTTP 응답 상태 코드 분류
 */
typedef enum e_http_status {
    HTTP_OK            = 200, /**< 요청 성공 */
    HTTP_BAD_REQUEST   = 400, /**< 클라이언트 요청 오류 */
    HTTP_NOT_FOUND     = 404, /**< 리소스를 찾을 수 없음 */
    HTTP_SERVER_ERROR  = 500  /**< 서버 내부 오류 */
} t_http_status;
```

#### 인라인 주석 규칙

```c
/* 섹션 구분 — 함수 내 논리 블록을 나눌 때 */

// 단일 라인 — C++에서 허용, C99 이후 허용
// 단, 파일 전체에서 한 가지 스타일만 사용한다

x = base * rate;  /* 후행 주석 — 짧고 필수적인 경우만 */
```

**쓰지 말아야 할 주석:**
```c
/* ❌ 당연한 것 */
/* 루프 시작 */
for (int i = 0; i < n; i++) { ... }

/* ❌ 코드를 그대로 번역 */
/* result에 a와 b를 더한 값을 할당한다 */
result = a + b;

/* ❌ 코드와 불일치하는 오래된 주석 */
/* 배열 크기는 10 */
int arr[20];
```

### Phase 3 — 코드 포맷 정리

주석 작성과 함께 코드 포맷을 일관되게 정리한다.

**원칙: 기존 코드베이스의 스타일을 먼저 파악하고 맞춘다.**
파일 전체에서 이미 사용 중인 스타일이 있으면 그것을 따른다.
스타일이 섞여 있으면 더 많이 사용된 쪽으로 통일한다.

#### 들여쓰기
- 탭 또는 스페이스 중 하나만 사용 (혼용 금지)
- 스페이스 사용 시 통상 4칸 (C/C++) 또는 2칸 (JS/TS)
- 기존 파일의 설정을 우선한다

#### 줄 길이
- 80자 권장, 최대 120자
- 주석 본문은 72자에서 줄바꿈

#### 공백
```c
/* 연산자 주변 */
x = a + b;          /* O */
x=a+b;              /* X */

/* 함수 호출 */
foo(a, b, c);       /* O */
foo( a,b,c );       /* X */

/* 포인터 선언 — 파일 내 통일 */
int *ptr;           /* C 스타일 */
int* ptr;           /* C++ 스타일 */

/* 조건문 */
if (x > 0) {        /* O */
if(x > 0){          /* X */
```

#### 브레이스 — 파일 내 통일
```c
/* K&R 스타일 (Linux/C 주류) */
if (condition) {
    ...
}

/* Allman 스타일 */
if (condition)
{
    ...
}
```

#### 빈 줄
```c
/* 함수 사이: 2줄 */
int foo(void) { ... }


int bar(void) { ... }

/* 함수 내 논리 블록 사이: 1줄 */
int process(void)
{
    /* 입력 검증 */
    if (!input)
        return -1;

    /* 처리 */
    result = compute(input);

    return result;
}
```

### Phase 4 — 검증

```bash
# clang-format이 있는 경우 포맷 검사 (선택)
clang-format --dry-run --Werror <파일>
```

체크리스트:
- [ ] 모든 public 함수에 `@brief` 이상의 주석이 있는가?
- [ ] `@param` 방향 지시자가 올바른가? (`[in]`, `[out]`, `[in,out]`)
- [ ] 주석이 현재 코드와 일치하는가? (오래된 주석 없는가?)
- [ ] WHAT이 아닌 WHY를 설명하는가?
- [ ] 당연한 것을 설명하는 주석을 추가하지 않았는가?
- [ ] 포맷이 파일 전체에서 일관된가?
- [ ] 기존 코드베이스 스타일과 충돌하지 않는가?
