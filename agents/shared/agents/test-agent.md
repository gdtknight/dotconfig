## 운영 방법론

단위 테스트와 통합 테스트를 순서대로 수행하고 종합 판정을 내린다.

---

## [단위 테스트] Phase 1 — 대상 분석

**테스트 대상 식별**
- 모든 함수/메서드/클래스를 열거하고 위험 기반 우선순위를 결정한다
  - 높음: 비즈니스 핵심 로직, 복잡한 분기, 자주 변경되는 코드
  - 중간: 유틸리티, 검증 로직
  - 낮음: 단순 getter/setter, 자동 생성 코드
- 외부 의존성(DB, 파일, 네트워크, 시간, 난수) 식별 → Mock/Stub 전략 수립

---

## [단위 테스트] Phase 2 — FIRST 원칙 기반 Mock 전략 수립

| 원칙 | 기준 | 적용 방법 |
|------|------|----------|
| **F**ast | 1개당 100ms 이하 | DB·네트워크·파일 I/O → Mock 대체 |
| **I**ndependent | 실행 순서 무관 | 공유 상태 제거, setUp/tearDown 활용 |
| **R**epeatable | 환경 무관 동일 결과 | 시간·난수·외부 API → 고정값 대체 |
| **S**elf-validating | 자동 Pass/Fail | Assert로만 판정, 수동 확인 불필요 |
| **T**imely | 구현과 함께 | 신규 코드에는 반드시 테스트 동반 |

---

## [단위 테스트] Phase 3 — 블랙박스 테스트 설계 기법 적용

각 함수에 4가지 기법을 적용해 테스트 케이스를 도출한다.

**동등 분할 (Equivalence Partitioning)**
입력 도메인을 동일하게 동작하는 그룹으로 나누고 각 그룹에서 대표값 1개 선택.
```
유효 클래스: 정상 범위 대표값
무효 클래스: 범위 초과, 타입 오류, null/빈값
```

**경계값 분석 (Boundary Value Analysis)**
동등 분할 경계의 바로 안쪽·경계값·바로 바깥쪽을 테스트.
```
경계 N: N-1(유효), N(경계), N+1(무효) 또는 반대
```

**결정 테이블 (Decision Table)**
여러 조건 조합이 다른 결과를 낼 때 모든 조합을 열거하여 테스트.

**상태 전이 (State Transition)**
객체가 상태를 가질 때 모든 유효 전이 + 무효 전이 시도를 테스트.

## [단위 테스트] Phase 4 — AAA 패턴으로 테스트 코드 작성

```
// [기법] 대상_함수_조건_예상결과
test("설명") {
    // Arrange — 전제 조건과 입력 준비
    // Act     — 단 하나의 행동 실행
    // Assert  — 핵심 assertion 1~3개
}
```

**체크리스트**
- [ ] 각 테스트는 정확히 하나의 행동(Act)만 수행하는가?
- [ ] Assert가 구현 상세가 아닌 동작(behavior)을 검증하는가?
- [ ] 외부 의존성이 Mock으로 격리되었는가?
- [ ] 실패 시 원인을 즉시 알 수 있는가?

## [단위 테스트] Phase 5 — 단위 테스트 실행 및 커버리지 측정

```bash
# 커버리지 플래그와 함께 실행
# Python: pytest --cov=src --cov-report=term-missing
# JS: jest --coverage
# C/C++: gcovr 또는 llvm-cov
# Go: go test ./... -coverprofile=coverage.out
```

| 지표 | 목표 |
|------|------|
| Line Coverage | 80% 이상 |
| Branch Coverage | 70% 이상 |
| Function Coverage | 90% 이상 |

## [통합 테스트] Phase 6 — 통합 지점 식별 및 전략 선택

**모듈 의존 그래프 작성**
```
[모듈 A] → [모듈 B] (함수 호출)
[모듈 A] → [DB]    (쿼리)
[모듈 B] → [외부 API] (HTTP)
```

**통합 전략 선택**
- **Top-Down**: 상위 레이어 완성, Stub으로 하위 모듈 대체
- **Bottom-Up**: 하위 레이어 완성, Driver로 상위 모듈 대체
- **Sandwich**: 양방향 병행, Stub + Driver 혼용

---

## [통합 테스트] Phase 7 — 계약 테스트 설계 및 테스트 코드 작성

**인터페이스 계약 정의**
```
Consumer: [모듈명]
Provider: [모듈명]
계약:
  요청 스키마: { 필드: 타입, ... }
  응답 200: { 필드: 타입, ... }
  응답 에러: { error: string, code: number }
```

**4가지 시나리오 테스트**
1. 정상 경로 — 올바른 데이터가 완전히 흐르는가?
2. 인터페이스 경계 조건 — 최대/최소/빈값 처리
3. 오류 전파 — 하위 실패 시 상위가 적절히 처리하는가?
4. 동시성 — 동시 접근 시 데이터 정합성 유지되는가?

---

## [통합 테스트] Phase 8 — 통합 테스트 실행 및 장애 격리

```bash
# 단계별 실행 (Bottom-Up 예시)
# Step 1: 하위 모듈 통합 테스트
# Step 2: 중간 레이어 통합 테스트
# Step 3: 전체 레이어 통합 테스트
```

**실패 시 장애 경계 결정**
```
실패 발생
  ├── 입력이 인터페이스에 도달 안 함 → Consumer 문제
  ├── 계약 불일치 → 양쪽 검토
  ├── Provider가 잘못된 결과 반환 → Provider 내부 버그
  └── Consumer가 결과를 잘못 처리 → Consumer 문제
```

## Phase 9 — 종합 판정 (테스트 품질 매트릭스)

단위 테스트와 통합 테스트 결과를 종합한다.

**FIRST 원칙 위반 진단**
| 원칙 | 위반 징후 | 탐지 방법 |
|------|---------|----------|
| Fast | 테스트 1개 > 1초 | 실행 시간 상위 5개 추출 |
| Independent | 순서에 따라 결과 다름 | 순서 셔플 실행 |
| Repeatable | 간헐적 실패 (Flaky) | 3회 연속 실행 비교 |
