## 운영 방법론

코드를 읽고 테스트 케이스를 설계한 뒤 실제 테스트 코드를 작성한다. 4개 Phase를 순서대로 수행한다.

---

### Phase 1 — 대상 분석 (무엇을 테스트할지 결정)

**1-1. 코드 구조 파악**
- 테스트 대상 함수/메서드/클래스를 모두 열거한다
- 각 함수의 입력(파라미터 타입, 범위), 출력(반환 타입, 부수 효과), 의존성을 파악한다
- 외부 의존성(DB, 파일, 네트워크, 시간, 난수)을 식별한다 — 이것들은 Mock/Stub 처리 대상

**1-2. 위험 기반 우선순위 결정**
- 높은 우선순위: 비즈니스 핵심 로직, 복잡한 조건 분기, 자주 변경되는 코드, 버그 이력이 있는 코드
- 중간 우선순위: 유틸리티 함수, 검증 로직
- 낮은 우선순위: 단순 getter/setter, 자동 생성 코드

**1-3. 테스트 불가 항목 기록**
- 외부 시스템에 직접 의존하여 격리 불가한 코드를 명시
- 리팩터링 필요 여부를 함께 표시 (테스트 가능하게 만들려면 무엇이 필요한가?)

---

### Phase 2 — FIRST 원칙 기반 설계 방침 수립

Robert C. Martin의 FIRST 원칙을 각 테스트에 적용할 방법을 결정한다.

| 원칙 | 기준 | 적용 방법 |
|------|------|----------|
| **F**ast | 테스트 1개당 100ms 이하 | DB·네트워크·파일 I/O → Mock으로 대체 |
| **I**ndependent | 실행 순서에 무관하게 동일 결과 | 공유 상태 제거, setUp/tearDown 활용 |
| **R**epeatable | 환경에 무관하게 동일 결과 | 시간·난수·외부 API → 고정값으로 대체 |
| **S**elf-validating | 자동으로 Pass/Fail 판정 | 수동 확인 없이 Assert로 판정 |
| **T**imely | 구현 직전 또는 직후 작성 | 신규 코드는 구현과 함께 테스트 작성 |

각 외부 의존성에 대한 Mock/Stub/Fake 전략을 명시한다.

---

### Phase 3 — 블랙박스 테스트 설계 기법 적용

각 함수에 대해 아래 4가지 기법을 순서대로 적용하여 테스트 케이스를 도출한다.

**3-1. 동등 분할 (Equivalence Partitioning)**
입력 도메인을 동일하게 동작하는 그룹으로 나누고, 각 그룹에서 대표값 1개를 선택한다.
```
예) 나이 입력 (0~120 유효)
  - 유효 클래스: 0~120 → 대표값: 25
  - 무효 클래스 1: 음수 → 대표값: -1
  - 무효 클래스 2: 121 이상 → 대표값: 200
  - 무효 클래스 3: 비정수(null, 문자열) → 대표값: null, "abc"
```

**3-2. 경계값 분석 (Boundary Value Analysis)**
동등 분할 경계의 바로 안쪽·경계·바로 바깥쪽을 테스트한다.
```
경계 0: -1(무효), 0(유효 경계), 1(유효)
경계 120: 119(유효), 120(유효 경계), 121(무효)
```

**3-3. 결정 테이블 (Decision Table)**
여러 조건의 조합이 다른 결과를 낸다면 테이블로 모든 조합을 열거한다.
```
조건 A | 조건 B | 예상 결과
  T   |   T   |   ...
  T   |   F   |   ...
  F   |   T   |   ...
  F   |   F   |   ...
```
조합 폭발이 일어나면 조건별로 독립성을 확인하고 불필요한 조합을 제거한다.

**3-4. 상태 전이 (State Transition)**
객체나 시스템이 상태를 갖는다면 상태 다이어그램을 그리고 각 전이를 테스트한다.
```
상태: [초기] → [진행중] → [완료] → [취소]
각 전이 (유효 전이 + 무효 전이 시도)를 테스트 케이스로 만든다.
```

---

### Phase 4 — AAA 패턴으로 테스트 코드 작성

도출된 테스트 케이스 각각을 Arrange-Act-Assert 3구간으로 작성한다.

```
// [기법] 테스트_대상_함수명_조건_예상결과
test("나이가 0일 때 경계값 유효 처리") {
    // Arrange — 테스트 전제 조건과 입력 준비
    const age = 0;
    const mockLogger = createMock(Logger);
    const sut = new UserValidator(mockLogger);

    // Act — 테스트 대상 동작 실행 (단 하나의 행동만)
    const result = sut.validate(age);

    // Assert — 예상 결과 검증 (테스트 1개당 핵심 assertion 1~3개)
    expect(result.isValid).toBe(true);
    expect(result.error).toBeNull();
}
```

**테스트 이름 규칙**: `[테스트 대상]_[조건]_[예상 결과]` 또는 `Given_When_Then` 형식

**작성 시 체크리스트**
- [ ] 각 테스트는 정확히 하나의 행동(Act)만 수행하는가?
- [ ] Arrange에서 불필요하게 많은 것을 설정하고 있지 않은가? (테스트 냄새: Excessive Setup)
- [ ] Assert가 구현 상세가 아닌 동작(behavior)을 검증하는가?
- [ ] 테스트 실패 시 어떤 케이스가 왜 실패했는지 즉시 알 수 있는가?
- [ ] 외부 의존성이 Mock으로 적절히 격리되었는가?
