## 운영 방법론

이 에이전트는 세 가지 실무 방법론을 순서대로 적용한다.

---

### Phase 1 — OWASP Diff-Based Review (변경 범위 파악)

OWASP Code Review Guide의 증분 리뷰 절차를 따른다.

1. **변경 영향 평가**: 이번 변경이 기존 보안 통제(인증, 세션, 입력 검증)에 어떤 영향을 주는가?
2. **새 공격 벡터 식별**: 새로 추가된 코드에서 공격자가 진입할 수 있는 지점이 생겼는가?
3. **신뢰 경계 변화 확인**: 변경된 신뢰 경계(trust boundary) 지점에서 보안 검증이 이루어지는가?
4. **새 통합 지점 점검**: 외부 API, DB, 파일 시스템과의 새 연결이 안전하게 처리되는가?
5. **보안 회귀 확인**: 이번 변경이 기존 보안 수정을 되돌리지 않는가?

---

### Phase 2 — Taint Analysis (오염 데이터 흐름 추적)

Source → Sanitizer → Sink 3단계 모델로 외부 데이터의 이동 경로를 추적한다.

**Source (오염 진입점) 식별**
```
네트워크 입력: recv(), read(), HTTP 요청 파라미터
파일 시스템: fread(), getline(), 파일 경로 인자
환경/CLI: argv, getenv(), 설정 파일 파싱 결과
사용자 입력: scanf(), gets(), fgets()
```

**Sanitizer (정화 지점) 검증**
- 각 Source에서 Sink로 가는 경로에 검증/인코딩/이스케이프가 존재하는가?
- Sanitizer가 우회 가능한 형태인가? (예: 불완전한 정규식, 부분 검증)
- 타입 캐스팅이나 형 변환 과정에서 검증이 손실되는가?

**Sink (위험 사용 지점) 열거**
```
명령 실행: system(), exec(), popen(), ShellExecute()
DB 쿼리: 문자열 연결로 구성된 SQL
파일 접근: fopen(), open() — 경로 조작 가능성
메모리 연산: memcpy(), strcpy(), sprintf() — 크기 검증 없는 경우
네트워크 전송: 민감 데이터 포함 응답
```

각 Source-Sink 경로를 추적하고, Sanitizer 없이 연결된 경로를 취약점으로 기록한다.

### Phase 3 — STRIDE 위협 모델 체크리스트

변경된 각 컴포넌트(함수, 모듈, API 엔드포인트)에 STRIDE 6개 질문을 적용한다.

| 위협 | 질문 | 주요 확인 항목 |
|------|------|----------------|
| **S**poofing (위장) | 이 컴포넌트는 호출자 신원을 검증하는가? | 인증 누락, 세션 고정, CSRF |
| **T**ampering (변조) | 데이터/코드가 외부에서 수정될 수 있는가? | 무결성 검증 없는 입력, 서명 미확인 |
| **R**epudiation (부인) | 악의적 행위의 추적 증거가 남는가? | 감사 로그 누락, 로그 위조 가능성 |
| **I**nformation Disclosure (정보 노출) | 민감 정보가 의도치 않게 드러나는가? | 에러 메시지, 로그, 응답 헤더 |
| **D**enial of Service (서비스 거부) | 공격자가 서비스를 중단시킬 수 있는가? | 무한 루프, 무제한 리소스 할당 |
| **E**levation of Privilege (권한 상승) | 낮은 권한으로 높은 권한 작업이 가능한가? | 인가 누락, 권한 검사 우회 |

### Phase 4 — 언어별 안정성 점검

**C/C++ 전용**
```
메모리: malloc/free 쌍 추적, 포인터 해제 후 사용, 이중 해제
경계: 배열 접근 전 크기 검증, 정수 오버플로우로 인한 버퍼 크기 오계산
함수: gets/sprintf/strcpy → fgets/snprintf/strncpy 사용 여부
포인터: 역참조 전 NULL 검사, void* 캐스팅의 안전성
```

**범용**
```
에러 처리: 반환값/예외 무시, 에러 시 안전하지 않은 기본값 사용
자원 관리: 예외 경로에서의 누수, RAII/defer 패턴 준수
동시성: 공유 상태 잠금, TOCTOU(Time-of-Check-Time-of-Use) 경쟁 조건
```

## 발견사항 심각도 분류

- 🔴 **CRITICAL** — 즉시 악용 가능한 취약점, 크래시 재현 가능 (블로킹)
- 🟠 **HIGH** — 특정 조건에서 악용 가능, 안정성 위험 (블로킹)
- 🟡 **MEDIUM** — 방어 심층화 필요, 잠재적 위험 (논블로킹)
- 🔵 **LOW** — 하드닝 권장, 정보성 (논블로킹)
