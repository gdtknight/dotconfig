## 운영 방법론

대상 코드의 언어와 프로젝트 기존 컨벤션을 먼저 파악한 뒤, **WHY 중심의 문서화 주석 작성**과 **일관된 포맷 정리**를 수행한다 (`INSTRUCTIONS.md`, `engineering.md` 준수).

---

### Phase 1 — 코드 및 컨벤션 분석

1. 대상 파일의 언어와 프로젝트 내 기존 주석 스타일, 포맷터 설정(`.clang-format`, `.prettierrc`, `.editorconfig`, `ruff.toml` 등)을 확인한다.
2. 주석이 누락되었거나 현재 코드 동작과 불일치하는 공개(Public) 함수·클래스·구조체·열거형을 식별한다.
3. **절대 원칙**:
   - 이미 정확하게 작성되어 있는 기존 주석은 임의로 삭제하거나 문체를 바꾸지 않는다 (`engineering.md` 준수).
   - 주석 작성이 아닌 코드 로직·구조 변경(리팩토링)은 절대 수행하지 않는다.

---

### Phase 2 — 문서화 주석 작성

#### 1. 주석 작성 철학 (WHY > WHAT)
- **WHAT(코드가 하는 일)**을 그대로 번역하는 무의미한 주석(`i++; // i를 1 증가`)은 절대 추가하지 않는다.
- **WHY(설계 의도, 비직관적 제약, 전제 조건, 에러/예외 조건, 리소스 소유권/해제 책임, 참고 알고리즘)**를 간결하게 기술한다.
- 나쁜 코드를 주석으로 변명하기보다 필요한 제약 사항을 명확히 밝힌다.

#### 2. 언어별 표준 주석 형식
프로젝트의 기존 스타일을 최우선으로 따르며, 기준이 없을 때 아래 언어별 표준을 적용한다:

- **C / C++ (Doxygen `/** ... */`)**:
  ```c
  /**
   * @brief  함수의 핵심 역할을 한 줄로 요약
   * @param[in]     fd   대상 소켓 디스크립터
   * @param[out]    buf  수신 데이터를 저장할 호출자 버퍼 (최소 cap 바이트)
   * @return 읽은 바이트 수, 연결 종료 시 0, 실패 시 -1 (errno 설정)
   */
  ```
  - 단순 getter/setter나 자명한 헬퍼 함수는 한 줄 `/** @brief ... */`만 작성한다.
- **TypeScript / JavaScript (TSDoc / JSDoc `/** ... */`)**:
  - 타입 시스템이 이미 표현하는 타입 중복 표기는 생략하고 `@param`, `@returns`, `@throws`에 의미와 제약 조건만 기술한다.
- **Python (Docstring `"""..."""`)**:
  - 프로젝트 표준(Google / NumPy / PEP 257 스타일)을 따른다.
- **Go / Rust**:
  - 각각 `// FuncName ...` (GoDoc), `/// ...` (Rustdoc) 표준을 따른다.

---

### Phase 3 — 코드 포맷 정리

1. **프로젝트 공식 포맷터 우선 실행**:
   - 프로젝트에 `clang-format`, `prettier`, `ruff format`, `gofmt`, `rustfmt`, `stylua` 등이 설정되어 있으면 수동 편집 대신 포맷터 도구를 사용한다.
2. **수동 정리 시 기준**:
   - 파일 내 기존 들여쓰기(탭 vs 스페이스, 칸 수)와 브레이스 스타일(K&R vs Allman)을 100% 그대로 따른다.
   - 사용자가 지정한 대상 파일 외부의 주변 파일 포맷은 건드리지 않는다.

---

### Phase 4 — 검증

- 포맷이나 주석 추가 후 문법 오류나 빌드/린트 깨짐이 없는지 컴파일러·린터(`clang-format --dry-run`, `tsc --noEmit`, 테스트 실행 등)로 확인한다 (`accuracy.md` 준수).
