## 운영 방법론

리팩토링 계획을 받아 실제 코드 변경을 수행한다. **Green → 변경 → 테스트 → Green → 커밋** 사이클을 엄수한다.

---

### Phase 0 — 실행 전 상태 확인

```bash
# 현재 테스트가 전부 통과하는지 확인
# Green 상태가 아니면 리팩토링 시작 금지
```

**체크리스트:**
- [ ] 테스트가 전부 통과(Green)하는가?
- [ ] 작업 대상 파일이 명확한가?
- [ ] 적용할 리팩토링 기법이 정해졌는가?
- [ ] 한 번에 하나의 기법만 적용할 준비가 됐는가?

---

### Phase 1 — Baby Steps 실행 원칙

**절대 원칙:**
1. **한 스텝 = 하나의 리팩토링 기법** — 여러 기법을 동시에 적용하지 않는다
2. **리팩토링 커밋 ≠ 기능 변경 커밋** — 절대 섞지 않는다
3. **Red → 즉시 Revert** — 테스트가 실패하면 수정하지 말고 되돌린다
4. **동작은 보존한다** — 리팩토링은 외부 동작을 바꾸지 않는다

**Baby Steps 사이클:**
```
[Green 확인]
    ↓
[코드 변경 — 가능한 최소 단위]
    ↓
[테스트 실행]
    ↓ Green?
   Yes → [커밋: "refactor: 기법명 — 대상"]
    ↓
[다음 스텝]
    ↓ Red?
   No  → [즉시 Revert] → [더 작게 분리해서 재시도]
```

---

### Phase 2 — 기법별 실행 절차

각 리팩토링 기법의 안전한 실행 순서를 따른다.

**Extract Method (메서드 추출)**
```
1. 추출할 코드 블록의 경계를 정확히 정한다
2. 새 메서드 시그니처를 결정한다 (파라미터, 반환값)
3. 새 메서드를 작성하고 원본 코드를 호출로 교체한다
4. 테스트 실행 → Green 확인
5. 커밋
```

**Move Method (메서드 이동)**
```
1. 이동할 메서드가 어느 클래스에 더 적합한지 확인한다
2. 대상 클래스에 메서드를 복사한다
3. 원본 메서드가 새 메서드를 위임하도록 수정한다
4. 테스트 실행 → Green 확인
5. 원본 메서드의 모든 호출자를 새 메서드로 교체한다
6. 테스트 실행 → Green 확인
7. 원본 메서드 제거
8. 커밋
```

**Replace Conditional with Polymorphism (조건→다형성)**
```
1. 각 조건 분기를 Extract Method로 추출한다
2. 기반 클래스(또는 인터페이스)를 만든다
3. 각 분기에 대한 서브클래스를 만든다
4. 각 서브클래스에 추출한 메서드를 Override한다
5. 조건문을 다형성 호출로 교체한다
6. 단계마다 테스트 실행 → Green 확인
7. 커밋
```

**Replace Nested Conditional with Guard Clauses (중첩→가드절)**
```
1. 가장 바깥쪽 예외 조건을 먼저 처리하는 Guard Clause로 변환한다
2. 테스트 실행 → Green 확인
3. 다음 조건을 반복해서 변환한다
4. 커밋
```

**Introduce Parameter Object (파라미터→객체)**
```
1. 새 데이터 클래스를 생성한다
2. 메서드 시그니처에 새 클래스를 파라미터로 추가한다 (기존 파라미터는 아직 유지)
3. 테스트 실행 → Green 확인
4. 기존 파라미터를 새 객체의 필드 접근으로 교체한다 (하나씩)
5. 단계마다 테스트 실행 → Green 확인
6. 기존 파라미터를 제거한다
7. 커밋
```

---

### Phase 3 — 대규모 리팩토링: Strangler Fig Pattern

단일 함수/클래스 수준을 넘어 모듈/시스템 수준의 리팩토링이 필요한 경우.

**실행 절차:**
```
1. 라우팅 레이어(Facade)를 만든다 — 구 코드와 신 코드 사이의 중재자
2. 가장 작은 기능 단위 하나를 선택한다
3. 새 구현체를 작성하고 테스트를 통과시킨다
4. 라우팅 레이어에서 해당 기능을 신 구현체로 전환한다
5. 기존 코드는 아직 삭제하지 않는다
6. 충분히 검증된 뒤 기존 코드를 제거한다
7. 다음 기능 단위로 반복한다
```

**원칙:** 한 번에 하나의 기능만 전환한다. 전환과 삭제를 같은 커밋에 하지 않는다.

---

### Phase 4 — 단계별 검증

각 리팩토링 스텝 후 다음을 확인한다.

**동작 보존 확인**
```bash
# 테스트 실행
# 이전 스텝과 동일한 결과인지 확인
```

**의도하지 않은 변경 감지**
```bash
# git diff로 변경 범위가 계획한 것과 일치하는지 확인
# 예상 외의 파일이 변경되지 않았는지 확인
```

**커밋 메시지 형식**
```
refactor: [기법명] [대상 함수/클래스]

예시:
refactor: Extract Method — processPayment에서 validateCard 분리
refactor: Replace Conditional with Polymorphism — OrderProcessor.process()
refactor: Introduce Parameter Object — UserService.createUser()
```
