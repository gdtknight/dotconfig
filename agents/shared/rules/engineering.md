# Engineering Rules

## 1. 구조 설계 및 추상화 원칙

### 새 함수·클래스·파일 생성 기준 (Fewest Elements)
새 함수·클래스·파일은 아래 넷 중 하나를 수행할 때만 만든다. 지우고 호출부에 펼쳤을 때 더 읽기 어려워지지 않는다면 만들지 않거나 인라인(Inline)한다.
- 호출자가 몰라도 되는 결정이나 복잡함을 숨긴다
- 코드만 봐서는 드러나지 않는 의도에 이름을 붙인다
- 지켜야 할 조건(불변식)을 한 곳에서 강제한다
- 지금 당장 필요한 교체 지점이다 (테스트 대역 등)

**추상화 경고 신호 (즉시 제거 대상)**:
- 몸체가 받은 인자를 그대로 다른 함수에 넘기는 한 줄뿐이다 (Pass-through)
- 이름이 감싼 호출보다 정보를 더 주지 않는다
- 감싼 래퍼와 감싸지 않은 직접 호출이 혼용된다 (같은 일을 하는 방법이 둘이 되지 않게 한다)

### 함수·메서드
- 함수는 **한 가지 일(SRP)**만 하며, 내부의 **추상화 수준을 일관**하게 유지한다 (`connectDB()`와 `i++`를 한 함수에 섞지 않는다).
- 파라미터는 **4개 이하**를 유지한다. 초과하면 의미 있는 구조체/Parameter Object로 묶는다.
- 결과는 **반환값으로** 돌려주며, 여러 함수가 같은 결과 변수(`out` 파라미터)를 넘겨받아 채우게 하지 않는다.
  - 단, C 언어처럼 반환값을 에러 코드(`0`/`-1`)로 쓰거나 호출자가 할당한 버퍼를 채우는 시스템 API 관용 패턴은 예외로 한다.
- 길고 복잡한 조건식은 1회성이면 **설명 변수(Explaining Variable)**로 먼저 풀고, 복잡한 도메인 규칙이거나 재사용될 때만 의도를 드러내는 이름의 함수로 추출한다.

### 이름 및 상수
- 이름은 **의도를 드러낸다**. `data`, `temp`, `x`, `flag`, `val`이나 타입 접두어(`strName`, `intCount`)는 쓰지 않는다.
- 함수 이름과 실제 동작이 일치해야 하며, 부수 효과가 있으면 이름에 드러낸다 (POLA).
- 의미가 불분명한 매직 넘버·문자열은 이름 있는 상수로 교체한다 (`if (status == 3)` 금지).
  - 단, 의미가 바로 옆 코드나 주석에서 자명한 값(문법상 위치, 진법 `10`/`16`, 고정 길이, `fd`의 `-1` 등 관용 리터럴, 알고리즘 고유 상수)은 리터럴 그대로 쓴다.
  - 상수는 사용하는 곳 가까이에 둔다 (단일 파일이면 파일 상단, 여러 파일이 공유·조정하면 공용 상수 모듈/헤더).

### 모듈·클래스 및 중복(DRY)
- **높은 응집도·낮은 결합도**: 모듈 내부 요소는 하나의 목적으로 묶고 모듈 간 의존 파급을 최소화한다. 전역 상태(Global State)를 무분별하게 사용하지 않는다.
- **데메테르 법칙**: 도메인 객체 간 `a.getB().getC().doSomething()` 형태의 내부 결합 체인을 만들지 않는다 (단, 순수 데이터 구조체/DTO/설정 탐색이나 Fluent API·Stream 체이닝은 예외).
- **실용적 추상화 (YAGNI)**: 인터페이스(DIP·OCP)와 다형성 분리는 **교체·변경이 실제로 반복되는 곳**에만 둔다. 구현이 하나뿐이고 바뀔 계획이 없으면 구체 타입에 직접 의존한다.
- **중복(DRY) 판단 기준**: 같은 **지식·결정**(한쪽을 고칠 때 다른 쪽도 반드시 고쳐야 하는 코드)이 두 곳 이상에 있을 때만 추출한다. 단순 호출 문법의 반복이나 변경 이유가 다른 **우연한 유사성**은 추출하지 않는다.

## 2. 방어적 프로그래밍 및 보안

- **Fail Fast & 입력 검증**: 외부에서 온 모든 데이터(네트워크, 파일, CLI, 사용자 입력, 외부 저장소)는 신뢰하지 않고 진입점에서 즉시 검증·거부한다.
- **에러를 삼키지 않는다**: 빈 `catch` 블록, 무시한 반환값·에러 코드, 미처리 Promise rejection을 남기지 않는다. 의도적으로 무시할 때는 반드시 이유를 주석으로 남긴다.
- **에러 메시지의 구체성**: 에러 메시지는 원인과 컨텍스트를 함께 담는다 (`"Error occurred"` 금지).
- **리소스 정리**: 메모리, 파일 디스크립터, 소켓, 락, 타이머, 이벤트 리스너는 모든 경로(정상·오류·언마운트)에서 누수 없이 해제한다.

## 3. 주석 및 테스트

- **WHY 중심 주석**: 새로 작성한 복잡한 로직에는 무엇(WHAT)이 아닌 **"왜(WHY)"** 주석을 남긴다. 나쁜 코드를 주석으로 변명하지 말고 코드 자체를 개선하며, **기존 코드의 정상 주석은 건드리지 않는다.**
- **테스트 검증**: 테스트 스위트가 있는 프로젝트에서 동작을 바꾸면 공개된 동작(Behavior)과 엣지 케이스(빈 값, 경계값, null, 에러 경로)를 검증하는 테스트를 함께 추가·수정한다.
- **테스트 무결성**: 실패하는 테스트를 임의로 지우거나 `skip` 처리하여 통과시키지 않는다. 테스트 자체가 틀렸다고 판단되면 근거와 함께 먼저 보고한다.
